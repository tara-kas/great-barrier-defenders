# Reef Rescue AUV — one-minute demonstration

Record **one uninterrupted 60-second screen capture of the running application**. Keep the mission clock, speed multiplier, controller source and event log visible. Camera changes and a clearly labelled speed change are acceptable; do not splice separate episodes, jump the simulation clock, replace the camera feed with a render, or label a scripted decision as Gemini. Captions may be added over the continuous take without covering evidence.

The main story is one eligible transfer interrupted by an operator-injected current wave: the wave changes the simulated water load, the grip fails in the model, and the robot autonomously recovers and places **the same fragment**. This is a demonstration of bounded recovery in a reduced simulator, not a claim of coral healing or real-world robustness.

The timetable below is still the target; it is not evidence that these services are deployed. Use stage-specific captions and preserve their real latency in the continuous take.

- During 23–43 seconds, show the changed sensor/fragment state reaching the base station, a fresh plan/route response, and the local controller accepting or rejecting it before recovery.
- During 43–54 seconds, make local safety authority visible. To claim disconnected autonomy, rehearse and measure the appropriate disconnected run; remote Gemma on Modal does not count as onboard perception.
- During 54–60 seconds, show which components genuinely ran, with model/solver IDs and measured latency. Do not label the local two-route heuristic as cuOpt.

Measured on 8 November: one live Argon planning request on actual browser telemetry took **16.7 seconds**. Gemma/camera and cuOpt were not part of that check. The full connected 60-second sequence has not been rehearsed or recorded; budget both inspection calls, planning/recovery calls and motion before accepting this timetable. Do not edit out service latency or accelerate model execution in the evidence.

Keep the explicitly labelled scripted take as a fallback. The legacy cloud-Gemini instructions below describe a separate supported mode, not the new onboard architecture.

## Prepare and rehearse

1. Launch `python3 scripts/run_lab.py` and open `/lab/`. Use a fixed exported scene, initially seed 42, with **one required placement** (`missionGoal: 1` in the scene JSON). Preserve a healthy eligible donor, a bleached living same-genet recipient, a wrong-genet healthy control and a dead control. In the default registry these can be `donor-1` / `recipient-1` (`G1`), `donor-2` (`G2`) and `reef-1` (dead). Check the imported registry rather than assuming these IDs in a different scene.
2. Start with current **0.08 m/s**, visibility **8 m**, autonomous pilot and a rehearsed route. Show paths, sonar, tool-camera view and the sensor stream. Disable manual pilot and clear all queued faults. Do not randomize during the recorded take; save the tested seed and scene. Use mixed reef topology and moving schools as context without obscuring the operation.
3. Use **Scripted** for the primary take when no Gemini credential is configured. The exact source caption is **“Local scripted control · synthetic sensing”**. Do not hide that label. A hosted static page alone is not the Gemini backend.
4. For a Gemini take, configure the server key, explicitly select Gemini and first complete a real camera-plus-sonar request. Confirm `source: gemini`, a matching pending decision ID, a provider interaction/model, the actual image hash/time and a validated local outcome. The caption becomes **“Gemini cloud supervision · local safety control”**. Measure provider latency in rehearsal; it is real wall-clock time and cannot be edited out of a continuous take. If a call fails, retain the visible hold. Restart a rehearsal explicitly rather than silently substituting scripted output.
5. Rehearse the complete one-placement episode with the current-wave fault. Choose a visible simulation speed, normally **4× or 8× during transit**, returning to **1× for the key inspection/grip-loss view** if the measured schedule permits. Keep the actual multiplier on screen. The timings below are recording targets, not permission to force mission states. Adjust the legitimate scene/transit length and speed before recording until all required events fit. If verification has not happened by the final window, the take does not yet meet the planned evidence sequence.
6. Before claiming UV inspection, verify that the **actual inspection phase activates the visible inspection signal in the rendered tool camera**. `inspect_recipient` / `inspect_donor` must agree with the renderer's lamp mode; a renderer checking only a phase containing `scan` will miss those phases. Invisible UV is represented by a labelled visible pilot/fluorescence proxy, not a calibrated UV camera. A violet light alone is not a detection result.
7. Verify the new current-wave behavior before filming: inject it only while `robot.holding` names a carried fragment; observe increased current/load followed by modeled grip loss. A direct “Drop fragment” command is a different test and must not be presented as a wave-caused failure. If the wave only triggers safe hold, show that truthfully or fix/retest the modeled load-to-grip link before using the main storyboard.
8. Clear the telemetry recorder immediately before the take. Keep a separate wall-clock recording timer. Save the scene, episode/event export and 5 Hz telemetry JSONL after capture. The recording is exactly 60 seconds; evidence exports are supporting artifacts, not replacement footage.

Before accepting a take, check the actual exported state and events:

- The source label matches reality: `scripted` or a real `gemini` response. An unavailable provider is never a successful VLM demonstration.
- The injected current event precedes the grip-loss event, and the recorded modeled load/threshold supports the cause. A separately injected drop is not substituted.
- The fragment ID held before the fault equals the ID recovered and finally placed; donor stock is conserved and no replacement fragment silently appears.
- At least one drop and one recovery are recorded; exactly one required placement is mechanically verified; the episode's own `completed` flag is true. These are model outcomes, not biological outcomes.
- The pilot remains autonomous after fault injection; no manual movement/gripper/route intervention supplies the recovery. Spectator camera changes are recorded separately from robot control.
- The 60-second recording has no hidden cuts, reset, clock jump or unlabelled acceleration. If any required check fails, rehearse again or present the failure honestly.

## Perception gap and the steps to close it

The baseline can show camera rendering, synthetic sonar/fusion and registry-gated autonomy today. Those alone do not establish a learned model recognized the scene. Close that gap with a verifiable chain rather than a more persuasive label:

1. Verify the tool-camera pose and active inspection mode against the rendered frame. Record **camera position, orientation, simulation timestamp, lamp mode and SHA-256 of the exact JPEG bytes** used for each decision. Timestamp/hash already supplied by an endpoint are not a substitute for logging camera pose; if pose is missing, record it before claiming the complete chain.
2. With working credentials, send that actual JPEG plus the synchronized sonar/fusion data and declared route alternatives to Gemini. Save the provider interaction ID, model, decision ID, response, latency and the server-returned image hash/time. Never use a mocked test response as live evidence.
3. Confirm that the returned action/route is in the allowed set and belongs to the still-pending decision. The local controller must retain registry eligibility, clearance and outcome checks even if the VLM is wrong. Record the accepted/rejected decision and actual subsequent behavior.
4. Rehearse visible positive and negative controls: eligible same-genet living pair, wrong-genet donor, dead recipient, and degraded camera/sonar conditions. Compare the actual responses and holds; do not infer general perception accuracy from one hand-selected successful image.
5. Keep the distinction explicit in the final take: **rendered camera evidence**, **synthetic sonar**, **known registry facts**, and **Gemini's real interpretation** are different sources. If the rubric requires on-device learned perception, that remains an additional deployment/measurement task; cloud Gemini does not satisfy it by relabelling.

Do not attempt to squeeze every feature into one minute. A continuous, observable failure-to-recovery chain with honest source labels is stronger evidence than an unverified list of capabilities.
